# R30 mixed / noncatalog checkout integration map

Prepared from source reads only on 2026-10-13. Repository: `/Users/zainllw0w/.codex/worktrees/r30-media-integration/site`. No ORM execution, tests, provider calls, Git actions or repository edits were performed for this map. Foundation 38 must release before importing foundation 39 changes. Approval models being prepared by the private worker are not assumed to exist yet.

## Existing canonical path

1. Current owned selection capture → `ig_revision_checkout._source_cart_control()` → `ig_revision_cart_binding.build_cart_binding()` → per-line `selection_readiness(strict=True)` → `validate_checkout_items()` → `bind_quote_lines()`.
2. `checkout_authority_control()` / `authorize_revision_checkout()` authorize the current customer purchase source. `prepare_revision_checkout()` owns publication, proposal/token creation and crash replay.
3. `ig_checkout.create_or_update_proposal()` validates quote/current owner, synchronizes deal and episode with `_sync_deal_and_episode()`, replaces current proposal items with `_replace_proposal_items()`, and appends the frozen `_revision_snapshot()`.
4. Browser POST `storefront.views.ig_checkout.ig_checkout_proposal()` invokes `ig_checkout_generation.create_or_reuse_generation_invoice()` for assisted V2. `_prepare_generation()` invokes `_revalidate_frozen_proposal()`, locks recipient/payment choice, calls `_snapshot()`, persists the original frozen cart in PaymentAttempt and reserves inventory before provider dispatch.
5. `monobank._apply_payment_attempt_status()` routes a generation-backed attempt to `apply_generation_provider_status()` / `apply_verified_generation_payment()`.
6. `apply_verified_generation_payment()` retains the existing single winner under `_lock_generation_graph()`, validates exact provider amount/identity, commits generation resources, invokes `orders.payment_attempts.materialize_payment_attempt()` and `ig_checkout_payment.bind_verified_payment()` in one atomic boundary.
7. `materialize_payment_attempt()` validates original attempt provenance, uses the stable checkout-series Order key, bulk creates exact OrderItems, binds their real IDs to the expanded source map, and records conversion. `bind_verified_payment()` links attribution/assignment/deal/episode/payment lifecycle and paid inventory ownership.

No alternative invoice, payment winner, custom Order creator or fake catalog Product is necessary or acceptable for this extension.

## Minimum private interfaces to agree with approval worker

Names below are proposed interface shapes, not implemented or inferred model names.

1. `resolve_approved_custom_line(scope, line_id, approval_reference, *, lock)` returns a finite result or typed verified capability. It validates exact client, episode, selection session/generation/revision/reset floor, recipient/line, approved terms version, authenticated manager actor, owned source/design references, and distinct authority responsibilities. Missing/pending/stale/foreign/ambiguous must be explicit non-ready outcomes. A price approval alone does not authorize manufacturing feasibility, physical stock, delivery date or payment truth.
2. `validate_custom_quote_line(capability, accepted_configuration)` returns immutable commercial facts: stable custom identity, exact title/garment configuration/color/size/fit/customization and reference digest, positive bounded quantity, finite exact-cent unit/line amounts, currency, explicit payment/promo policy and resource authority. No model price, free text approved marker or option_values string can construct the capability.
3. `freeze_custom_checkout_line(verified_line, owner)` produces a versioned detached line envelope suitable for proposal revision and original PaymentAttempt snapshot. Original owner scope and commercial digest are sealed together. Unknown keys, swapped approval versions, boolean-as-integer IDs, NaN/infinite money and schema downgrade reject.
4. `verify_frozen_custom_checkout_line(envelope, original_owner)` is the common validator used by snapshot/provenance/materializer before Order effects. It must be capability-verifying, not merely a dataclass type check or accepted status string. Original paid attempts retain exact frozen terms; new revision/approval cannot replace them. Whether revocation of an issued but still payable invoice requires provider cancellation/review is a deliberate owner policy, not silent mutation.
5. `custom_resource_authority(verified_line)` chooses an explicit untracked/made-to-order approval or an exact existing warehouse/catalog resource allocation. It never infers stock from title/size/color. Commitment and fulfillment continue using the existing inventory owners. If no verified mapping exists, block/review instead of silently skipping.

The private worker owns authoritative approval responsibilities/models. This integration adapter owns transport of their verified result into the existing checkout. The response/model controls may identify an approval reference for lookup but cannot grant it.

## Invariants to preserve

- Existing all-catalog v1 snapshots, quote digests, legacy absence semantics and provider/payment behavior remain valid unchanged.
- Custom requires explicit typed approval. `product_id=null`, `kind=custom`, `is_custom=true`, arbitrary reference strings, metadata IDs or option_values do not grant authority by themselves.
- Exact line/recipient identities and order are preserved, including mixed same-recipient and different-recipient lines. Every paid economic row binds to actual OrderItem ID.
- Combined total, negotiated discount, promo eligibility and prepayment/COD policy are computed once; title/configuration change invalidates commercial digest.
- One existing generation winner creates one existing canonical Order. Paid loser cannot create another; amount mismatch/late stock issue remains resource/reconciliation review under existing owner.
- Pending manager approval/proposal stays a proposal; no fake Order before verified payment. Verified manager commercial terms never fabricate provider-paid revenue.
- Catalogue stock paid-consumption and warehouse actual fulfillment happen once. Custom untracked status is explicitly approved, never guessed.
- Customer-account user is current authenticated owner only; IG @username identity does not imply siteUser association by phone/email.
- Shared admin/IG/customer display consumes accepted human facts; internal IDs/approval capability contents/private reference tokens remain private.

## Minimum new proof cases

1. Real authoritative custom approval producer → current source acceptance → proposal/revision → V2 invoice preparation (provider mocked at network boundary) → verified winner → one canonical Order with exact custom OrderItem and IG assignment; rerun returns identical Order/Item IDs.
2. Mixed catalogue bundle expansion plus one custom row retains original line/recipient identity and exact real item IDs; catalog pricing/digest unchanged, custom quote included once, combined total exact.
3. Missing any required approval responsibility, source acceptance, owner binding or resource authority yields zero proposals/tokens/attempts/provider calls/Orders; approved price without feasibility/availability cannot be promoted.
4. Fake option_values approval marker, ordinary null product, arbitrary custom_print_lead_id, foreign capability, wrong client/episode/line/recipient, swapped version and custom/catalog kind substitution all reject.
5. Custom facts/price/currency/quantity/reference/configuration tamper before invoice rejects before provider effects; attempt envelope or actual item-map tamper rolls back Order and conversion marker together.
6. Late original paid attempt after new episode/reset/manager approval still binds its exact original frozen scope or existing explicit late-review path; it never relabels to latest approval.
7. Concurrent/duplicate provider successes and paid loser preserve one Order and stock-once behavior with mixed/custom cart.
8. Expired/cancelled approval and invoice reissue respect existing provider ambiguity safeguards. No new invoice without prior identity/terminal proof. Terms cannot change through browser POST.
9. Explicit custom full-only/discount-ineligible policy remains enforced in mixed promo/200+COD attempts; no eligibility unlocked by product=null.
10. Exact custom display facts round-trip to admin/IG; owned authenticated customer order only appears in account; private capability/reference IDs never display.
