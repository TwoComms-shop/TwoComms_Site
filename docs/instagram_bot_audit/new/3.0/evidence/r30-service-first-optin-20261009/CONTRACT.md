# Сервисный приоритет и приглашение к подписке

Статус: ✅ код/native/production приняты; release `bb1c83f17a043d158e1bc4736a0b2d9820933b1f`. Подробности в PRODUCTION_RELEASE_2026-10-09.md.

## Подтверждённый инцидент

Ограниченное read-only чтение production на `fe51309b9`: клиент 351 сообщил в source3334, что доставка стоила 90 грн, а взяли 120 грн, и отметил негативное первое впечатление. Анализ2948 распознал `support_complaint`. После этого сохранены manager echo3337/3338 с объяснением стоимости, предложением возврата разницы и извинением. Revision202 не содержит generation proposal; source3334 не содержит Gemini request/model. Response-debt receipt113 уже передал ответственность менеджеру.

В последних 40 сохранённых сообщениях отдельного MODEL-ответа о бонусе после жалобы нет. Ранее отправленное приглашение3330 — manager/native Direct echo с сервисным вопросом и UGC-предложением. Оно было отправлено по прежнему поручению владельца. Поэтому версия «Gemini ответил бонусом на жалобу» не установлена этими данными. Raw переписка и provider identifiers остаются в приватном локальном журнале, не в Git. Повторный ответ этому клиенту не требуется; возврат денег не считается выполненным по одному обещанию в тексте.

## Подтверждённые пробелы в коде

- Лексический SUPPORT_RE не покрывает расхождение согласованной и фактической стоимости доставки. Негативное первое впечатление также может не попасть в сервисный маршрут.
- `manager_case_reason` зависит от manager control/обещания самой модели. Ошибочный ответ без передачи может не создать реальное задание команде.
- Проверка ответа блокирует покупочный CTA, но допускает отдельную фразу о бонусе, сторис или промокоде.
- Рекламные guards преимущественно ждут exchange/return case или результата анализа. Свежая собственная жалоба до анализа не защищена общим правилом; consent sender не проверяет сервисный риск.
- Карточка приглашения содержит две кнопки. Владелец просит одну положительную кнопку; неподтверждённое согласие по тексту или молчанию недопустимо.

## Контракт исправления

1. Собственная текущая жалоба получает сервисный приоритет независимо от покупочной истории и рекламных сигналов. Связь с USER source, namespace, reset и privacy сохраняется. Чужие цитаты, гипотетические ситуации, нейтральные вопросы о цене доставки и «проблем нет» не становятся претензией автоматически.
2. Ответ признаёт ситуацию, содержит уместное извинение и следующий шаг проверки командой. Реальное source-bound manager task/notification/receipt создаётся до отправки. Это постановка на проверку, а не доказательство, что руководство уже прочитало сообщение. Суммы клиента остаются сообщёнными, а не подтверждённой финансовой истиной.
3. Пока обращение не разрешено, не отправляются рекламные предложения, приглашения UGC/подписки и скидки. Guard проверяется при подготовке и непосредственно перед HTTP; новое входящее сообщение может остановить старое предложение. Сервис остаётся доступным. MID/partial/UNKNOWN не переписываются и не повторяются. Известная остановка до claim остаётся PENDING/attempts0 с cooldown5мин; после claim — terminal FAILED/attempts1 по existing MariaDB ledger, без replay. Противоречивый MID сохраняется как UNKNOWN.
4. Подписка предлагается отдельно после подтверждённой оплаты до отправки заказа, только в допустимом стандартном окне. Одна положительная кнопка; отсутствие нажатия ничего не меняет. Старые подписанные ответы «нет» принимаются по прежнему контракту. Отзыв согласия остаётся доступным отдельно.
5. UK/RU/EN тексты выбираются по собственному источнику клиента. Кнопка не обещает немедленную скидку: UGC10 требует проверки сторис, дополнительные5 — actual purchased-product link, stars и staff moderation. Тот же unused code и исходные90дней сохранены.
6. Уже состоявшийся manager reply сохраняет существующую ответственность и предотвращает дублирующий автоматический ответ. Оплата, стоимость доставки, компенсация и shipment не изменяются этим блоком. Настоящий новый вопрос о цене сохраняется в original response plan даже без выбранного товара; manager control сервисного ответа не закрывает этот вопрос. Вопросительные слова проверяются целиком: «взяли» не создаёт ложное «ли».

## Приёмка и остаток

Выполнены native MariaDB regressions source→purpose→durable task→candidate/final response и races рекламных отправок:501scenarios/498PASS/3existing manual concurrency skips. Однокнопочная actual quick-reply форма, ignored answers, старый decline/revoke, source drift и pre-shipment guards приняты. Scoped commit/push/canonical SSH pull, runtime/SHA и авторизованный browser подтверждены в release evidence. Естественный новый клиентский контакт, три отдельные two-worker concurrency gates и прочие purpose/native future grant остаются открытыми. Production не является тестовым fixture.

Откат: scoped revert на main, документированный SSH pull и обновление процессов; не удалять сохранённые receipts/tasks и не переписывать уже отправленные приглашения.
