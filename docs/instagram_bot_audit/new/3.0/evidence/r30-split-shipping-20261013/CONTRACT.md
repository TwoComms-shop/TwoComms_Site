# Engineering37 — раздельные отправления и согласованные условия

✅ Реализовано, проверено и деплойнуто `0527d2f925a7e928e8493d827f03fe462e784655`. [Production receipt](PRODUCTION_RELEASE_2026-10-13.md).

## Границы решения

Подписанная актуальная проверка всей корзины → отдельное неизменяемое предложение двух вариантов → доказанная native SENT-карточка → подписанный выбор клиента → один существующий экономический заказ → точное распределение всех OrderItem/количеств по посылкам → реальные ТТН, отдельные движения склада и carrier snapshots → получение всех исходных товаров → один post-purchase шаг.

Цена доставки не выводится из желания «отдельно» или manager free-text. Для каждой посылки менеджер подтверждает плательщика и максимальную сумму для клиента в UAH; клиент видит сумму и общую стоимость каждого варианта. Фактическая сумма может быть ниже согласованного лимита; превышение не допускается без нового согласования. При оплате продавцом стоимость для клиента равна нулю. Доставка перевозчику не становится выручкой магазина. Изменённые условия требуют новой версии и нового выбора.

Вместе — одна группа всей корзины; отдельно — 2–20 групп, каждая строка со всем её количеством ровно в одной группе. Разделение количества одной строки между группами пока не поддерживается и не должно скрыто терять единицы. Сроки подготовки/отправки берутся из исходной проверки, прибытие не гарантируется. WAIT обсуждается в предложении, но выбор доставки не обходит полный обычный stock/quote/payment gate и не создаёт фиктивную доступность будущего товара.

Существующие SourceCart→Proposal→Generation→Payment→OrderItem provenance обязательны. Ни zip, ни похожий SKU, ни новый частичный заказ не заменяют точную связь. COD распределяется один раз по всей корзине с сохранением суммы в копейках; второй посылке не копируется весь остаток оплаты.

В этом срезе менеджер регистрирует реальные уже оформленные ТТН каждой посылки после фактической передачи именно её товаров в отправление. Форма явно объясняет, что подтверждение списывает эти товары со склада один раз. Автоматическое создание нескольких документов НП — отдельный следующий контракт; старый whole-order creator для split блокируется до provider I/O. Подтверждение менеджера не подменяет carrier-доказательство получения. Stock и paid commitments списываются только для точных единиц этой посылки, повтор операции не списывает их снова.

Частичная передача отображается на своей посылке. Общий Order становится `ship` только после полного покрытия подписанного manifest фактическими dispatch-квитанциями всех посылок; money, loyalty и scalar ТТН при этом не переписываются. Запрос маркетингового согласия «до отправки» блокируется уже по первому shipment journal. `done` и запрос отзыва требуют реального carrier-получения всех посылок.

Оставшийся приоритетный контракт: частично доступная корзина, где S/M можно отправить сейчас, а L ожидается позже. Этот срез не резервирует будущий товар и не разрешает первую посылку при WAIT остальных строк; для оплачиваемого плана пока нужна доступность всей корзины. Не выдавать обсуждение отдельных посылок за реализованное исполнение backorder. Изменение уже привязанного плана также требует отдельного amendment-контракта.

Native UNKNOWN/partial delivery предложения не даёт согласия и не повторяется вслепую. Чужой/copy payload, голое «да», старая версия, mixed inbound с уточнениями, устаревшая корзина/epoch/config/privacy не исполняют выбор. Marketing consent не расширяет окно Meta; сервисные две кнопки Together/Separately не относятся к правилу одной positive marketing кнопки.

Production — только scoped migration/release и read-only runtime; никаких fixtures/тестовых ТТН/проверочных сообщений настоящим клиентам. Все 27 полных паспортов остаются частичными. UGC90 дней и тот же unused10→15% не меняются.
