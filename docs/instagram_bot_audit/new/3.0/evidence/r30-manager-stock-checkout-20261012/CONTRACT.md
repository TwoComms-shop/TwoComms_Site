# Block 35 · Manager stock reconciliation → ordinary checkout

Requested by the owner 12.10.2026: an exact, physically available item outside the accounting ledger must be orderable after manager confirmation, with a polished, usable interface.

The existing availability decision is dialogue evidence. This block adds a separate, explicit, audited confirmation of the **absolute physical inventory count**, never a per-client increase or an unlimited stock bypass. Catalogue shared variant capacity and exact size capacity are separate counts. Warehouse capacity is one unambiguous actual StockItem. Disabled configuration and ambiguous/untracked stock require the appropriate owner to resolve them.

The manager sees the accounting count, live and paid commitments, the exact selection, and the minimum count supporting it. A signed preview binds the decision, current source/cart/owner/configuration, actual inventory identities and reservation history. A changed preview rejects the operation. A unique operation identity and immutable receipt prevent replay from restocking goods twice.

When actual source evidence confirms purchase, reconciliation and ordinary source-bound proposal/reservation preparation commit together. Availability-only enquiries reconcile inventory without inventing purchase consent, an offer or a payment link. Incomplete or changed selection, unsupported configuration, unavailable lines, price/provenance errors or insufficient confirmed capacity roll the whole operation back. Mixed regular-stock/unrecorded AVAILABLE positions keep the full basket; WAIT lines are never silently excluded. The manager availability decision supplies no price, payment recognition or delivered-order authority. No customer/provider HTTP is part of this action.

Production catalogue variants are currently MyISAM; size rules, warehouse stock and reservations are InnoDB. The migration converts the variant inventory parent to InnoDB so existing allocation row locks and the new count/audit/proposal transaction have real transactional semantics. No fake receipt or compensating stock write substitutes for rollback.

Acceptance requires real native MariaDB tests for stale/replayed actions, two clients competing for one unit, paid commitments past TTL, full-cart and exact configuration/source changes, failed-checkout rollback, ordinary reservation/payment/order/fulfilment continuity, permission and privacy guards. UI is checked with real local authenticated actions and production authenticated rendering at 320/390 px. Production is never a test fixture. SHA/schema/runtime/browser receipts are recorded separately after deployment.

Full split execution, route-based arrival guarantees, future native marketing capability and full passport acceptance are separate open work. Existing UGC 90-day rules stay unchanged.

The manager action requires an existing enabled exact catalogue size rule. An untracked NULL size cap is explicitly counted and becomes a numeric cap; a missing/disabled rule remains an editor decision. Ordinary reservations now protect the effective exact-size cap through every actual item in grouped reservations, including paid commitments after TTL. Catalogue payment consumes both shared stock and the numeric size count atomically. Existing negotiated offers retain their validated source-backed price and payment policy; stale evidence or catalogue changes reject reconciliation instead of repricing silently.

Native current reads under allocation-parent locks preserve capacity after another transaction commits. Busy reservation edits deny promptly without ignoring capacity; foreign protected item reads use SKIP LOCKED with complete-identity coverage checks and a typed retry condition, avoiding the existing item-before-variant editor edge. Initial full-basket holds transfer to the first invoice generation under the same locks, one exact pool at a time. Warehouse write-off locks all parent identities in numeric order before reserving or changing movements.

An uncertain HTTP result retains the exact original request, decision digest, UUID and counts. Refresh cannot replace it with another case. Only its verified receipt settles the operation; retry submits the same operation. Historical receipts survive changed baskets, but current-source binding is separately read back before continuation. No unsupported customer confirmation, payment or send is implied by the stock-only outcome.
