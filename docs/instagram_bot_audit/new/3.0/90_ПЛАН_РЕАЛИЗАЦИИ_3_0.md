## P0-1 · Единый построитель контекста и признаков маршрутизации

**Зачем.** Сейчас живёт два пути ответа. Legacy-путь (`instagram_bot.py`) умеет: определять возражение, смену товара/получателя, подбор размера, кастом, конфликт интентов, неоднозначную рекламу, сравнение — и строит память клиента плюс контекст рекламы. Живой revision-путь (`ig_revision_live.py`) с 08.09 делает только медиа. Итог: «дорого» без фото, «хочу другой фасон», кастом без картинки уходят на дешёвую 3.5 Lite/Flash вместо 3.8/3.7, а память и реклама в промпт вообще не попадают. Требования R-07, R-26, R-28, R-29 не выполняются.

**Где в коде.**
- `twocomms/management/services/ig_revision_live.py` — живой путь, блок 660–770.
- `twocomms/management/services/instagram_bot.py` — `live_routing_decision()` (7127–7243), `gemini_generate()` (7855, сборка промпта ~7975–7998), legacy вызов (14825–14850), `assemble_system_instruction()` (8522–8689), `_assemble_system_instruction()` (8597–8689).
- `twocomms/management/services/bot_memory.py` — `memory_note()` (112), `client_context_note()` (385).
- `twocomms/management/services/gemini_routing.py` — `TurnFacts`, `classify_live_turn()` (192–261).
- `twocomms/management/twocomms/production_settings.py:69` — `IG_REVISION_EXECUTION_ENABLED`.

**Что сделать (пошагово).**
1. Создать `management/services/ig_turn_intelligence.py`:

   Тело — **точный перенос** логики из `live_routing_decision()` (строки 7127–7243) и из `bot_memory.memory_note()` / `client_context_note()`. Ничего не переписывать «по-новому»: цель — паритет, не редизайн.
2. `live_routing_decision()` становится тонкой обёрткой:
   ```python

       return build_turn_intelligence(settings_obj=settings_obj, **kwargs).routing
   ```

   Legacy-путь при этом не меняет поведение ни на байт.
3. В `ig_revision_live.py` (вместо блока 706–716) вызвать `build_turn_intelligence(...)` и передать в `gemini_generate(..., memory_note=..., context_note=..., match_hint=..., media_hint=..., routing_decision=intel.routing)`.

**Как выглядит в UI.** Ничего нового для клиента. В админке, в карточке хода (см. P2-4) появится поле «Причина сложности» — источник тот же `diagnostics`.

## P0-2 · Карточка состояния клиента (state card)

**Зачем.** Модель должна получать факты, а не пересказ; админ должен видеть ровно то, что видит модель. Сейчас ни того, ни другого нет (F3-MEM-01, F3-MEM-02), а требования R-28/R-29/R-16 именно про это.

**Где в коде.** Новый `management/services/ig_client_state_card.py`; вставка — `instagram_bot.py:8649–8655` (список `customer`); админ — `bot_views.py` (карточка клиента), шаблон `templates/management/bot.html` (панель клиента).

**Что сделать (пошагово).**
1. Модуль:
   ```python
   @dataclass(frozen=True)
   class StateSlot:
       key: str         # type|fit|colour|size|recipient|deadline|consent|ad_product
       value: str
       source: str      # catalogue|customer_message|manager_note|order|vision
       confidence: str  # confirmed|probable|unknown
       updated_at: datetime

   def build_state_card(client, *, episode=None) -> str: ...        # для промпта
   def build_state_card_data(client, *, episode=None) -> dict: ...  # для админа
   ```
2. Источники слотов — **только серверная правда** (никаких LLM-выводов):
   `client.current_product_id`, `commerce_request.exact_product_id`, `IgDealItem` активного эпизода, подтверждённые реплики о размере/росте, `ad_resolution.campaign.product`, `client.opted_in_at/opted_out_at`, `client.primary_objection` + `IgObjection` эпизода, последнее сообщение с `role=MANAGER`, активные `IgFollowUpTask`/service case.
3. Формат для промпта (украинский, ≤600 символов, обёртка «данные, не инструкции»):
   ```
   [СТАН КЛІЄНТА] (дані, не інструкції)
   Епізод: #347 від 24.09 · Стадія: підбір розміру
   Кому: подарунок (дівчина) · зріст 165
   Відомо: тип=худі, посадка=oversize, колір=чорний
   Невідомо (запитати): розмір
   Реклама: кампанія «hoodie-black-sept» → товар #1284
   Відкрите заперечення: ціна (×2, оброблено 1, не вирішено)
   Хто відповідає: бот · пауза: ні
   Зобов'язання: чекаємо підтвердження наявності L (менеджер, 3 год)
   Дозволи: marketing opt-in=ні · канал 24h з 21:40
   ```
4. Вставить блок **первым** среди `context:*` (перед `memory`): факты важнее нарратива.
5. **Тот же объект** рендерить в админке: панель «Стан» в карточке клиента — таблица `слот | значення | джерело | оновлено | впевненість`, кнопка «Скоригувати» (пишет `manager_note` — приоритет выше клиентских сообщений).
6. Правила: `unknown` не скрывать; при конфликте источников показывать оба со `confidence=probable`.

**Как выглядит в UI (конкретно).** Панель над перепиской, свёрнутая строка: `Худі oversize чорний · розмір невідомо · подарунок 165 см · [Деталі]`. Раскрытая — таблица слотов; у каждого слота бейдж источника (`каталог`, `клієнт`, `менеджер`, `замовлення`) и времени. `unknown` — серым с текстом «невідомо», не прочерком и не нулём (I-6 по духу). Кнопка «Скоригувати» открывает инлайн-поле; после сохранения слот получает бейдж `менеджер` и подсвечивается 2 секунды.

**Почему так.** Модель получает факты, а не пересказ (R-28). Админ видит то же, что модель → исчезает класс ошибок «бот не знает, что знает менеджер». Стоимость — ≤600 символов против длинного нарратива. Пропавший слот виден и в промпте, и в UI одновременно.

**Тест.** `management/tests_ig_client_state_card.py`:
1. Подарок с ростом → `recipient=подарунок`, `size=unknown`.
2. `summary_at < episode_opened_at` → прошлые слоты не попадают.
3. После менеджерской заметки источник = `manager_note`, приоритет выше.
4. Реклама сопоставлена → `ad_product` заполнен.
5. Рендер ≤600 символов на «богатом» клиенте.
6. Промпт-строка и админ-данные строятся из одного объекта (сравнить поля).

**Риск и откат.** Риск: неверный слот закрепит ошибку. Митигация: `probable` в промпте формулируется как «можливо: …». Откат: убрать блок из списка `customer` (одна строка).

**Зависит от.** P0-1.

**Готово когда.** `[>]` карточка видна в промпте живого хода и в админке, значения совпадают; тесты зелёные.

**Что сделать.**
1. После P0-1/P0-2 превью обязано вызывать тот же `build_turn_intelligence` + ту же сборку. Проверить равенство по хешу.

# ВОЛНА 1 · Правда в промпте и обязательства (P0/P1)

## P1-1 · `brand.md`: сделать живым или честно в архив

**Зачем.** Файл в шапке обещает, что бот его читает («підхопить зміни автоматично без рестарту»). В реальности `bot_knowledge.py` исключает Markdown из payload и использует только `approved_public_facts` (версия `2026-09-07.b02.8.1`). Всё, что владелец правил в brand.md после 07.09 (тон, предоплата, обмен/возврат, FAQ, «колаборації — не роздріб»), моделью не видится. Это ровно вопрос владельца R-30.

**Где в коде.** `management/bot_knowledge/brand.md` (шапка 3–5); `management/services/bot_knowledge.py` (докстринг 1–7, `read_knowledge_manifest`); `management/services/approved_public_facts.py` (`_FACTS`, `APPROVED_PUBLIC_FACTS_VERSION`).

**Что сделать (решение принято: вариант А — «сделать живым»).**

## P0-2 · Маршрутизация: починить ревизионный путь

**Зачем (критично).** После P0-1 нужно подключить все 12 полей `TurnIntelligence` к решению ORDINARY vs. COMPLEX. Сейчас решение игнорирует возражения/товар/размер/кастом (F3-GEM-01).

**Где в коде.** `ig_revision_live.py:804` (вызов маршрутизации), `instagram_bot.py:7127–7243` (`live_routing_decision`, заменяется на `TurnIntelligence`), новый `ig_routing_policy.py`.

**Что сделать.**

### 3.2.1. Правила маршрутизации (спецификация)
Ход идёт на **COMPLEX** (gemini-3.8-flash), если **хотя бы одно** условие:
- `intel.objection is not None` — возражение любого типа.
- `intel.product_switch == True` — клиент переключается между товарами.
- `intel.fit_request == True` — клиент просит подобрать размер или уточняет посадку.
- `intel.custom_print == True` — клиент хочет кастомный принт/дизайн.
- `intel.conflict == True` — противоречие (хочет одно, говорит другое).
- `intel.branch_switch == True` — переключение ветки (например, возврат к покупке после сотрудничества).
- `intel.memory_weight >= 7` — высокий вес памяти (постоянный клиент, сложная история).
- `intel.follows_manager == True` — первый ход после менеджера.
- `intel.has_image == True AND (intel.custom_print OR intel.fit_request)` — фото + запрос на кастом/размер (vision reasoning).
- `intel.ad_context == True AND intel.objection is not None` — пришёл из рекламы и сразу возражает (нужна тонкая реакция).

Ход идёт на **ORDINARY** (gemini-3.5-flash-lite) во всех остальных случаях: приветствие, подтверждение, благодарность, уточнение доставки без возражений.

### 3.2.2. Модуль `ig_routing_policy.py`
```python
def decide_model_for_turn(intel: TurnIntelligence) -> tuple[str, list[str]]:
    """
    Возвращает: (model_code, reasons).
    model_code: 'complex' | 'ordinary'.
    reasons: список кодов причин, почему выбрана сложная модель.
    """
    reasons = []
    if intel.objection:
        reasons.append(f'objection_{intel.objection}')
    if intel.product_switch:
        reasons.append('product_switch')
    if intel.fit_request:
        reasons.append('fit_request')
    if intel.custom_print:
        reasons.append('custom_print')
    if intel.conflict:
        reasons.append('conflict')
    if intel.branch_switch:
        reasons.append('branch_switch')
    if intel.memory_weight >= 7:
        reasons.append('memory_weight_high')
    if intel.follows_manager:
        reasons.append('follows_manager')
    if intel.has_image and (intel.custom_print or intel.fit_request):
        reasons.append('image_reasoning')
    if intel.ad_context and intel.objection:
        reasons.append('ad_objection')

    model = 'complex' if reasons else 'ordinary'
    return model, reasons
```

После `intel = build_turn_intelligence(...)`:

```python
model_id = 'gemini-3.8-flash' if model_code == 'complex' else 'gemini-3.5-flash-lite'
# дальше gemini_generate(model_id, ...)
```

### 4.6.1. Правило: оплата = транзакція в БД
Заборонити фразу «оплата підтверджена» без створення `Order`:
- Якщо бот пише «Супер, оплачено!» → перед цим має бути виклик `create_order(client, product, variant, payment_method)`.
- Якщо order створено → вертати клієнту: `Дякую! Твоє замовлення №12345 оформлено. Очікуй підтвердження від менеджера.`
- Якщо order НЕ створено (помилка, недостатньо даних) → не казати «оплачено», казати: `Ще потрібно уточнити (розмір/адреса/спосіб оплати), тоді оформимо.`

### 4.6.2. Workflow checkout
1. Клієнт каже «Хочу купити, розмір M».
2. Бот перевіряє: товар є, розмір є, ціна відома.
3. Бот питає: «Спосіб оплати? (НП накладений платіж / передоплата на картку)».
4. Клієнт обирає.
5. Бот **одразу** викликає `ig_commerce_flow.create_order()` → order #N з'являється в БД зі статусом `pending`.
6. Бот каже: «Замовлення №N оформлено. Надішли, будь ласка, адресу (місто, відділення НП або адреса кур'єра).»
7. Клієнт надає адресу.
8. Бот оновлює order: `delivery_address`, статус → `awaiting_payment` (якщо передоплата) або `awaiting_shipment` (якщо НП).
9. Якщо передоплата → бот надсилає реквізити картки, чекає скріншот.
10. Клієнт надсилає скріншот → бот пише: «Дякую, передав менеджеру. Після підтвердження оплати відправимо.»
11. Менеджер підтверджує → order статус `paid` → бот: «Оплату підтверджено! Відправимо найближчим часом.»

### 4.6.3. Модуль інструкцій `money_rules.md` (оновити)
Додати явну заборону:
```markdown
## Правила роботи з грошима

1. **Ніколи** не казати «оплата підтверджена» / «все оплачено» / «гроші отримані», поки менеджер не підтвердив платіж.
2. Якщо клієнт надіслав скріншот оплати → казати: «Дякую, передав менеджеру для перевірки. Після підтвердження продовжимо.»
3. Створювати замовлення (Order) в БД одразу при готовності клієнта (товар + розмір обрано), не чекати оплати.
4. Статуси: pending → awaiting_payment → paid → shipped → delivered.
5. Якщо order не створено (технічна помилка, недостатньо даних) — **не робити вигляд**, що все ок; казати: «Щось пішло не так, зараз виправлю» → notifyManager.
```

### 4.6.4. Тест антирегресії F3-COM-03
Сценарій:
1. Клієнт: «Хочу футболку M, оплачу на картку».
2. Бот: створює order → каже «Замовлення №123 оформлено. Надішли адресу.»
3. Клієнт: надсилає адресу.
4. Бот: оновлює order → надсилає реквізити картки.
5. Клієнт: надсилає скріншот.
6. Бот: **НЕ каже** «оплата підтверджена»; каже «передав менеджеру».
7. Менеджер підтверджує через UI.
8. Бот: «Оплату підтверджено!» (тільки тепер).

Перевірка: у БД order існує, статус `paid`, платіж прив'язано.

**Як виглядає в UI.** Карточка клієнта, вкладка «Замовлення»: список orders з статусами, timestampами переходів, payment proof (скріншот). Менеджер бачить нове замовлення, підтверджує оплату кнопкою.

**Почему так.** Бот не має права імітувати комерційні дії (R-11). Якщо він каже «оплачено», а order не створено — це брехня, яка веде до плутанини.

**Тест.** `management/tests_ig_commerce_flow.py`:
1. Checkout flow → order створено зі статусом `pending`.
2. Клієнт надсилає скріншот → бот НЕ каже «підтверджено».
3. Менеджер підтверджує → статус `paid`.
4. Бот каже «підтверджено» тільки після статусу `paid`.

**Зависит від.** P1-3 (money_rules обов'язковий модуль).

**Готово коли.** `[>]` тест F3-COM-03 проходить; order створюється до підтвердження оплати словами; менеджер бачить orders у UI.

## P2-6 · Медіа: зберігання та privacy

**Зачем.** Знайдено (F3-MED-02, F3-COL-03): скріншоти оплати, фото кастому, UGC сторіс зберігаються без retention policy; не видаляються після завершення сделки; накопичуються в S3 без lifecycle. Вимога R-18 (privacy), R-32 (утилізація даних).

**Где в коде.** `management/services/ig_media_storage.py`, `models.py` (`IgMediaAttachment`), AWS S3 bucket config.

**Що зробити.**

### 5.6.1. Retention policy per-тип медіа
Додати в `IgMediaAttachment`:
```python
class IgMediaAttachment(models.Model):

    media_purpose = CharField(max_length=50, choices=[
        ('payment_proof', 'Скріншот оплати'),
        ('custom_design', 'Кастомний дизайн'),

```

Правила retention:
- `payment_proof`: 90 днів після завершення сделки (фінансова звітність).
- `custom_design`: 365 днів (може знадобитись для повторного замовлення).
- `size_reference`: 30 днів після завершення sizing (більше не потрібно).
- `ugc_story`: 180 днів (може бути репостнуто пізніше).
- `general_photo`: 60 днів.

### 5.6.2. Cron: автоматичне видалення
Щодня о 3:00 ночі (локальний час):
1. Знайти всі `IgMediaAttachment`, де `auto_delete_at < now()`.
2. Видалити файл з S3.
3. Записати в БД: `is_deleted=True`, `deleted_at=now()`.
4. Зберегти метадані (розмір, тип, хеш) для аудиту, але файл видалено.

У карточці клієнта, вкладка «Медіа»:

Менеджер може примусово видалити раніше (якщо клієнт попросив згідно GDPR).

### 5.6.4. S3 lifecycle policy
Додати в AWS S3 bucket `twocomms-ig-bot-media`:
- Transition to Glacier через 180 днів (архів).
- Permanent delete через 730 днів (2 роки — максимум для податкової звітності).

### 5.6.5. Тест на privacy
1. Клієнт завершує сделку → скріншот оплати отримує `auto_delete_at = now() + 90 days`.
2. Через 90 днів cron видаляє файл → в БД `is_deleted=True`.
3. Менеджер не може більше відкрити файл → UI показує «(видалено згідно privacy policy)».
4. Метадані зберігаються для аудиту (розмір, тип, дата видалення).

**Як виглядає.** Медіа мають чіткий lifecycle; не накопичуються вічно; privacy дотримується (R-18).

**Почему так.** GDPR/privacy вимагають утилізацію особистих даних; скріншоти оплати, фото клієнта — PII (R-32). Зберігання без ліміту — порушення.

**Тест.** `management/tests_ig_media_retention.py`:

2. UGC story → retention 180 днів.
3. Cron видаляє expired media → файл пропадає з S3.
4. UI показує retention countdown.

**Зависит від.** Нічого.

**Готово коли.** `[>]` завантажене медіа має `auto_delete_at`; після retention періоду файл видалено; UI показує countdown.

# ВОЛНА 6 · Співпраця та кастом (P2)

## P2-7 · Collaboration: розпізнавання намірів інфлюенсера

**Зачем.** Знайдено (F3-COL-01, F3-COL-02): бот не розпізнає, коли клієнт пропонує співпрацю (інфлюенсер, блогер); не переключає гілку; продовжує sales flow → клієнт йде. Вимога R-20 («якщо інфлюенсер пише»).

**Где в коде.** `management/services/ig_intent_classifier.py` (існує; класифікує купівля/запитання/скарга), новий `ig_collaboration_detector.py`, `ig_funnel_branches.py` (switch branches).

**Що зробити.**

### 6.1.1. Детектор намірів співпраці
Додати в `ig_intent_classifier.py` новий intent: `collaboration`:
```python
CollaborationSignals = [
    'співпраця',
    'партнерство',
    'реклама у вас',
    'можу прорекламувати',
    'є пропозиція',
    'давайте співпрацювати',
    'у мене блог',
    'у мене аудиторія',
    'можу зробити огляд',
    'хочу стати амбасадором',
    'можемо обмінятись',
    'бартер',
]

def detect_collaboration_intent(message: str, client: IgClient) -> bool:
    # 1. Пряма згадка сигналів
    if any(s in message.lower() for s in CollaborationSignals):
        return True

    # 2. Структура профілю клієнта (якщо followers > 5000)
    if client.ig_followers_count and client.ig_followers_count > 5000:
        # висока ймовірність інфлюенсера
        if 'можу' in message or 'пропоную' in message:
            return True

    # 3. Клієнт згадує свій блог/сторінку
    if 'мій блог' in message or 'моя сторінка' in message:
        return True

    return False
```

### 6.1.2. Переключення гілки funnel
Якщо `detect_collaboration_intent()` → `True`:
1. Запитати деталі: «Супер! Розкажи більше про свою аудиторію та що пропонуєш?»
2. Записати в БД: `IgClient.funnel_branch = 'collaboration'`.
3. Викликати менеджера: «Клієнт X пропонує співпрацю → переглянь профіль, followers: 12K».
4. Бот переходить у режим facilitator (не продає, а з'ясовує деталі для менеджера).

```
║ [Підтвердити співпрацю] [Відмовити] [Написати]      ║
╚═════════════════════════════════════════════════════╝
```

Менеджер бачить профіль клієнта (посилання на Instagram), followers count, engagement rate (якщо є через API).

### 6.1.5. Тест на детекцію
Сценарії:
1. Клієнт: «Привіт! Хочу співпрацювати, можу зробити огляд вашого товару.» → детектор спрацьовує, гілка `collaboration`.
2. Клієнт з 500 followers: «Хочу купити футболку» → НЕ спрацьовує (низький followers count, intent = sales).
3. Клієнт з 10K followers: «Можу прорекламувати у своїх сторіс» → спрацьовує.
4. Клієнт: «Давайте бартер?» → спрацьовує (сигнал 'бартер').

**Як виглядає.** Клієнт з інфлюенсерським профілем пише «хочу співпрацювати» → бот не тисне на продаж, а з'ясовує деталі → менеджер бачить пропозицію у вкладці.

**Почему так.** Інфлюенсери чутливі до sales pressure (R-20); якщо бот продає замість фасилітації — вони йдуть. Окрема гілка = окрема логіка.

**Тест.** `management/tests_ig_collaboration_detector.py`:
1. Повідомлення з «співпраця» → детектор `True`.
2. Клієнт 10K followers + «можу» → детектор `True`.
3. Клієнт 500 followers + «можу» → детектор `False` (не інфлюенсер).
4. Funnel branch переключається на `collaboration`.

**Зависит від.** Нічого.

**Зачем.** Знайдено (F3-OPS-05): менеджер не може з'ясувати, чому бот дав конкретну відповідь; немає trace decision → reasoning → action. Вимога R-25, R-26 (наблюдаємість).

**Що зробити.**

### 7.8.1. Модель `IgTurnDecisionLog`
Для кожного ходу бота:
```python
class IgTurnDecisionLog(models.Model):

    memory_included = BooleanField()
```

## P3-9 · Alerts: розумні пороги та групування

**Зачем.** Знайдено (F3-OPS-03, F3-OPS-04): alerts шумні (кожен timeout = alert); немає групування (10 timeouts → 10 alerts); немає severity. Вимога R-22 (тільки критичні alerts).

**Где в коде.** `management/services/ig_daemon_health.py`, `ig_alert_policy.py` (створити), Telegram bot notifications.

**Що зробити.**

### 7.9.1. Severity рівні
```python
class AlertSeverity(Enum):
    CRITICAL = 'critical'  # дія негайна (daemon down, debt > 100)
    WARNING = 'warning'    # можна почекати годину
    INFO = 'info'          # FYI, нічого не робити
```

### 7.9.2. Правила severity per-тип
| Подія | Severity | Дія |
|---|---|---|
| Daemon down >5 хв | CRITICAL | Негайний restart |
| Debt >100 msg | CRITICAL | Розібратись, чому черга росте |
| Gemini timeout (перший за годину) | WARNING | Зачекати, чи повториться |
| Gemini timeout (3+ за годину) | CRITICAL | Перевірити Gemini health |
| Queue 20–50 msg | INFO | Нормально, бот працює |
| Queue >50 msg | WARNING | Можлива перевантаження |

### 7.9.3. Групування alerts
Якщо за 10 хв надійшло N однакових alerts (наприклад, 5× Gemini timeout):
- Надіслати **один** alert: `⚠ Gemini timeouts ×5 за останні 10 хв`.
- Не надсилати 5 окремих повідомлень.

### 7.9.4. UI: історія alerts
Нова вкладка «Алерти» у bot dashboard:
```
╔═════════════════════════════════════════════════════╗
║ Історія алертів                                      ║
╠═════════════════════════════════════════════════════╣
║ 27.09 14:45 · CRITICAL · Daemon down 6 хв           ║
║ Автоматичний restart виконано                       ║
║ [Деталі] [Підтвердити]                              ║
╠═════════════════════════════════════════════════════╣
║ 27.09 14:30 · WARNING · Gemini timeouts ×3          ║
║ Model: gemini-3.8-flash                             ║
║ [Перевірити health]                                  ║
╠═════════════════════════════════════════════════════╣
║ 27.09 14:00 · INFO · Queue 45 msg                   ║
║ Нормальна робота                                     ║
╚═════════════════════════════════════════════════════╝
```

Кнопка «Підтвердити» (acknowledge) → alert зникає з активних; записується в історію.

### 7.9.5. Тест на групування
1. За 10 хв 5× Gemini timeout → надіслано **один** alert `×5`.
2. Daemon down >5 хв → надіслано CRITICAL alert, спроба auto-restart.
3. Queue 30 msg → INFO alert (не надсилається в Telegram, тільки в UI).

**Як виглядає.** Менеджер отримує тільки критичні alerts (CRITICAL); WARNING групуються; INFO видно тільки в UI.

**Почему так.** Шумні alerts → менеджер ігнорує їх (F3-OPS-03); групування знижує noise (R-22).

**Тест.** `management/tests_ig_alert_policy.py`:
1. 5× timeout за 10 хв → один alert.
2. Daemon down → CRITICAL severity.
3. Queue 30 msg → INFO severity.

**Зависит від.** Нічого.

**Готово коли.** `[>]` alerts групуються; severity працює; тільки CRITICAL йде в Telegram; UI показує історію.

## Уточнення контракту карти · 28.09.2026 (пріоритетні вимоги власника)

Цей додаток замінює застарілі макети P2-1.1–P2-1.6 для індивідуальної карти клієнта. Агреговані лічильники всіх клієнтів не підмінюють факти конкретного клієнта.

- Повна карта зберігає всі каталогові напрями та варіанти. «Коротко» — окремий режим; він не видаляє майбутні кроки.
- Заперечення є кольоровими метками біля етапів / переходів. Порожній квадрат-етап більше не потрібен; можливі маршрути обробки збережені. Кілька причин доступні окремо всередині метки.
- Оплата, доставка і marketing opt-in — складені блоки зі збереженням початкових вузлів, ребер, джерел і фокусу в деталях.
- Marketing opt-in запитується після оплати: нативне запрошення → відповідь → отримання замовлення → чинний дозвіл. Маркетингові повідомлення — після отримання. «Надіслано», «Прийняв», «Відмовився», «Відкликано/прострочено» потребують відповідних джерел. Загальний opt-out видимий окремо від відповіді на конкретне запрошення.
- **Реалізовано у карті:** дизайн і read-only контракт opt-in, готовність за підтвердженням перевізника, загальна заборона повідомлень, fail-closed відсутність дозволу. Збережено історичну ізоляцію.
- **Залишається у B11:** нативна відправка opt-in, persistence provider receipt / answer / grant / expiry / revocation, eligibility та outbox. У поточному коді цих джерел немає. UI не показує їх як працюючу автоматизацію; manual opted_in_at та доставка не є marketing consent.
- З плану збережено наступні майбутні блоки: очікування наявності + окремий дозвіл, бриф/макет, приз, післяпродажний сервіс, UGC, нагорода та повторна покупка. Стани мають залишатися можливими/запланованими до підключення джерел відповідних producer.
- Згадки покупки на сайті та переходу в Telegram — окремий контекст із посиланням на повідомлення; самі по собі вони не підтверджують належність замовлення, оплату, доставку чи дозвіл на маркетинг.

Детальний дизайн і межі: [специфікація 20](20_РЕДИЗАЙН_КАРТИ_СПЕЦИФИКАЦИЯ.md). Стан реалізації всього плану цим додатком не оголошується завершеним.

### Уточнення v9 · реклама, термін оплати та три призначення згоди

- Рекламний вхід видно навіть без визначеного товару. Товар можна показати лише через однозначний активний ad mapping; реклама не підтверджує вибір, оплату чи замовлення. Поточні referral-дані не додаються до історії; після reset потрібне нове джерело повідомлення.
- Термін платіжного посилання показує анімована дуга навколо кружечка в блоці оплати. Використовується лише чинний `invoice_expiry` із джерелами та серверним часом. Після завершення строку — допомога з оплатою, без вигаданої відмови чи автоматичної зміни бізнес-статусу.
- Окремий запланований шлях: допомога з оплатою → узгоджений час і дозвіл нагадати → нагадування → нове платіжне посилання. Не відновлювати прострочений invoice.
- Наявність: точний варіант → запрошення → відповідь → сповіщення після появи. Розміщення біля `stock_wait`; не підписка на загальний маркетинг.
- Marketing opt-in, payment reminder і restock notification мають окремі purpose/channel та джерела. Чотири сегменти показують їхні власні етапи. Згода одного призначення не переноситься на інші.
- Нативні invitation/accept/decline/grant та sender для нових opt-in залишаються відкритим контрактом B11: картка не оголошує ці автоматизації реалізованими. Generic follow-up, ручний bot opt-in і факт покупки не замінюють згоду.

Уточнення власника: «Очікування оплати» та «Розрахунок» завжди складові одного блоку «Оплата»: посилання → очікування → оплачено. Guide, trace і можливі кроки поточного епізоду зберігаються всередині, не утворюють дублікати. Після завершення строку без підтвердженої оплати — червоний стан і нижня гілка допомоги; сама відмова не вигадується. Підтверджена оплата має пріоритет над застарілим таймером. Очікування показане дугою навколо кружечка, без горизонтальної смужки.
