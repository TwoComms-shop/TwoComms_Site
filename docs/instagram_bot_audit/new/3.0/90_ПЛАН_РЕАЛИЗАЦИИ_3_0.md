## 0. Как пользоваться

1. Прочитать этот файл, `21`, соответствующие строки `22`, затем предметный код и AGENTS.md. Старые приблизительные номера строк не являются спецификацией API.
2. У каждого ID ниже один паспорт и один смысл. Старые повторные P0-1/2/3 из волны 3 и P1-4/5/6 из волны 4 устранены. Соответствие старым разделам — в `21`.
3. `depends_on` обозначает только прямые зависимости. Ссылки на другие задачи в пояснении не добавляют ребро зависимости. Отдельно указаны gates включения consumers.

   Gate применяется к затронутому срезу и его действующим consumers. Независимый read-only UI или existing instruction correction не ждут всех будущих функций плана; незавершённый обязательный safety contract этого среза при этом не обходится. Optional maintenance и future capability явно отделены ниже.
4. Статусы паспортов: `[ ]` контракт не реализован; `[~]` часть кода есть, полный контракт не принят; `[>]` конкретный срез подтверждён естественным live evidence; `[x]` этот срез принят владельцем; `[!]` внешний блокер с условием снятия; `[–]` снято явным решением. Датировать доказательства. Отдельный checklist «Выполненные блоки» ниже отмечает завершённую реализацию и выпуск; он не подменяет статус полного паспорта или gate естественного трафика.
5. Для каждой реализации записать в `08_ЖУРНАЛ_ВЫПОЛНЕНИЯ.md`: ID, scoped diff/commit, runtime/schema/flags, тесты, live evidence, остаток, следующий gate и откат. Новые файлы/модели в предложениях — проектные, не якобы существующие.
6. Сначала минимальный совместимый срез, затем измерение. Не заменять работающие FSM, catalogue resolver, payment settlement, private storage или publication flow ради нового названия.
7. Контракт завершения: **producer → durable evidence → consumer → фактический effect/receipt → UI**. Для read-only проекции effect не нужен; для бизнеса нарисованный узел или текст LLM effect не заменяют.
8. Делать атомарные совместимые релизы. Один commit на каждый пункт не обязателен, если producer/schema/consumer должны выпускаться вместе. Владелец разрешил реализацию, scoped commit/push/deploy каждого блока и отметки здесь; выполнять по AGENTS.md.

### Уточнення v9 · реклама, термін оплати та три призначення згоди

- Рекламний вхід видно навіть без визначеного товару. Товар можна показати лише через однозначний активний ad mapping; реклама не підтверджує вибір, оплату чи замовлення. Поточні referral-дані не додаються до історії; після reset потрібне нове джерело повідомлення.
- Термін платіжного посилання показує анімована дуга навколо кружечка в блоці оплати. Використовується лише чинний `invoice_expiry` із джерелами та серверним часом. Після завершення строку — допомога з оплатою, без вигаданої відмови чи автоматичної зміни бізнес-статусу.

Після завершення строку без підтвердженої оплати — червоний стан і нижня гілка допомоги; сама відмова не вигадується. Підтверджена оплата має пріоритет над застарілим таймером. **Первый совместимый вертикальный срез на existing producers:**

1. Зафиксировать свежий SHA/dirty/schema/flags; создать retained **обезличенные** multi-source fixtures §14.D. Mocks воспроизводят три validation причины отдельно и совместно. Capture actual provider payload, session, reply authority, projection и owner outcome. Не посылать реальные сообщения и не использовать production как fixture.
2. Перед generation идемпотентно собрать source facts из sealed bundle и допустимого current presentation context: explicit size/correction, purchase intent, exact/ambiguous model. После одной показанной позиции проверить owned SENT presentation/reply reference, episode/line, watermark/reset и отсутствие конфликтующих candidates. `Да` на фото не покупка; фото не подтверждает белый цвет/fit. При ambiguity сохранить L и задать один конкретный вопрос, не весь заказ заново.
3. Один bounded response plan различает **желание клиента**, **применимую configuration**, **авторизованную цену/наличие**, **checkout/effect authority**, **следующий вопрос**. Переиспользовать session/source_preferences/catalog/readiness/authority. Captured plan строит prompt/card/journey и проверяет ответ; denominator не скрывает partial facts. «Вы выбрали L» допускается по source choice; «L есть/заказ оформлен» — по соответствующему producer.
4. Согласовать advertised schema/controls с revision action path. Обычная selection не требует искусственного paylink/payment/handoff. Минимальный release может ограничить model controls поддержанным selection-путём и сохранять validated source choice; полноценный items path требует scoped authority/CAS/durable transition/replay. Просто удалить invalid control и отправить исходный текст нельзя: текст может обещать effect. Повторно валидировать весь ответ и semantic obligations.
5. Money/stock/order/consent guards сохранить. При incomplete pricing — полезный ответ о принятом размере и недостающем selector, без суммы. При exact pricing — canonical resolver/offer facts. Не глобально разрешать любую catalog цену/размер. Authority gap получает redacted named reason, не маскируется model failure.
6. Repair только для допустимой correction: pure eligibility/repair-plan check → atomic существующий lineage slot → final freshness/permission check → HTTP. Различать eligible/reserved/preparation/dispatch/unresolved. Crash/concurrent worker/supersession не создают дополнительный slot; dispatched/ambiguous repair не возвращается. Unsupported action не вращает модели с прежним prompt. Сохранить8/2/1 и free-project budget.
7. Из validated current facts дать substantive safe fallback через existing outbox с явным **semantic completion/coverage contract**: response plan перечисляет покрытые source/request obligations и оставшиеся, весь локальный ответ проходит semantic scope validation и final authority/CAS. Size acknowledgement не fake order и не ответ на весь одновременно заданный purchase request. Обычный SENT/`receipt_finalized` не должен автоматически закрыть непокрытые потребности bundle; сохранить durable coverage/disposition через existing source/revision/debt, без второго ledger. При непокрытом вопросе — recovery/manual owner; при корректном вопросе о действительно необходимом selector — явный next step и `waiting_on=customer`, а не бессмысленный retry до ответа клиента. Related inbound обновляет потребность/suppression; новый независимый вопрос отдельно не теряется. Ack необязателен; CAS и SENT/UNKNOWN suppression, не только текстовый hash.
8. Producer→source transition→read model→inline/full карта/карточка дают одинаковую scoped truth. Historical case352 сначала bounded dry-run/replay без customer send/invoice/order/provider I/O; reset/erased source не оживает, reviewed-no-reply автоматически не отменяется. Schema/config/code выпускать по AGENTS.md при отдельном запросе реализации/релиза.

**Почему так:** дополнительные ключи, более дорогая модель, длинный prompt, снятие price guard или замена фразы не устраняют расхождение selection, prompt capabilities и validator facts. Общий response plan/source producer позволяет полезно отвечать при неполном выборе со строгими business fences. Реальная недоступность данных/канала требует честного bounded outcome; обещание «идеально всегда оформит» не заменяет проверяемый контракт.

## 15. Уточнение владельца · повторные покупки и состав заказа · 06.10.2026

Это обязательное уточнение existing P0-1/2, P1-4/5, P2-1, P4-1/2/4, не новый паспорт. Код и UI должны одинаково различать текущий выбор, прежние заказы, добавление позиции, замену и отдельную новую покупку.

- Текущий эпизод содержит все позиции со стабильными line_id и получателями. «Добавьте ещё» в неоплаченный draft сохраняет первую вещь; «вместо чёрной розовую» заменяет только доказанный target. Несколько возможных целей требуют одного уточнения без произвольного active-line изменения. Один source MID применяет целый вектор операций атомарно и идемпотентно.
- Размер/цвет/модель/количество каждой позиции имеют собственный источник и историю supersession. Прошлое значение остаётся историей, не текущим подтверждением. Default qty1 — отдельный неподтверждённый контекст. Для двух вещей одинакового SKU нельзя потерять разных получателей или без доказательств придумывать отдельную доставку.
- Новая покупка получает отдельный episode/deal/proposal/generation/attempt/order scope. Прежний paid/Order/receipt не доказывает оплату нового заказа и не блокирует его через client-global latest deal. Незакрытый долг прежней покупки сохраняет собственного владельца. «Такую же» после закрытой покупки требует точного подтверждённого исторического target/copy intent; чужая, стёртая, неоднозначная или reset-invalid history не становится текущим выбором.
- Изменение draft переоценивает каталог, цену, наличие и полноту каждой позиции. Existing locked invoice/оплаченный заказ не переписывается из новой фразы: использовать canonical revision/generation/amendment boundaries. Callback старой оплаты остаётся при исходной покупке. Конкурентная смена даже неактивной позиции между quote и отправкой должна блокировать stale effect.
- Полный server-derived состав переносится через immutable proposal revision → generation → payment cart → exact OrderItem IDs. Bundle price splits сохраняют original line/recipient/quote mapping. Ни model items, ни active legacy compatibility fields не подменяют source authority.
- Карта показывает текущие позиции отдельно от реально связанных заказов. Исторический выбранный заказ доступен только для просмотра; текущие исправления не должны выглядеть изменением прошлого. «Первый/второй» допустимы только при доказанной полноте истории, иначе дата/ID и видимая partial coverage. Order не равен paid; количество покупок и LTV требуют точной принадлежности и refund-aware canonical money proof. При неизвестной сумме/возврате показывать неизвестность, не выдуманный доход.

Текущая реализация разбита на проверяемые блоки; полный контракт ещё открыт.
