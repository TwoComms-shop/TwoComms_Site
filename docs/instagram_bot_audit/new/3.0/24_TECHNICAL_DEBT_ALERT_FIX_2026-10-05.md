## Причины

1. Финальный CAS проверял наличие любого unprocessed inbox receipt для клиента,
   включая собственные echo. После первого фото Meta присылала echo до конца
   отправки ответа; уже подтверждённое собственное сообщение отменяло остаток
   плана. Это непосредственный источник двух исторических partial deliveries.
2. Монитор принимал совместимую UI-проекцию `send_state=unknown` за отдельный
   legacy send ledger. Эта проекция также обозначает частично доставленный,
   затем отменённый план. У неё намеренно отсутствует `send_started_at`, чтобы
   слабая сверка по тексту не переписала канонические revision receipts.
3. Дедупликация включала часовой bucket. Один неизменный fingerprint создавал
   новую Telegram-запись каждый час.
4. Конечная частичная доставка не имела своего класса в диагностическом
   инвентаре. Локальная финализация парковала её через технический claim token,
   а не через явную связь с существующей задачей на разбор.
5. Наличие долга могло подменять отдельный алерт о зависании runtime.
6. Refresh наблюдения перезаписывал fingerprint уже обработанного оператором
   случая. Новые source IDs могли ошибочно считаться уже подтверждёнными.
7. `run_instagram_periodic_jobs --dry-run` вызывал operational alert path.
8. Новый webhook `590` содержал `attachments[].type=ig_story` с полями
   `payload.story_media_id/story_media_url`. Парсер не извлекал вложение,
   echo validator возвращал `echo_empty`, ingress терял конкретный reason
   за общим `RevisionEchoDeferred` и бесконечно повторял те же байты.

## Реализованное исправление

- Общая read-only проверка ingress применяется и в финальном revision CAS,
  и в совместимых send paths. Она пропускает только accepted owner echo с
  **точным committed SENT bot effect** того же namespace, получателя и клиента.
  Раннее echo до receipt, неизвестная доставка, новый USER, manager echo,
  blocked receipt и неполная ограниченная выборка сохраняют send fence.
  Функция ничего не помечает обработанным; обычный ingress owner завершает
  materialization позже. Текстовое сходство и cache не дают исключения.
- `ig_story` нормализуется в story context в общих attachment parsers;
  сохраняются provider identity и исходный тип. Shared story не выдаётся за
  reply_to.story и не становится доказательством UGC reward.
- Отсутствующий URL допустим только для явной context-only ссылки с provider
  media/object identity. Пустые/невалидные вложения не превращаются в доставку.
  Исторический контекст не включает capture или текущий manager takeover.
- Echo refusal передаёт конкретный safe reason и retryability. Детерминированный
  отказ сохраняет исходный inbox receipt в BLOCKED для разбора без бесконечного
  retry. Остальные materialization failures имеют bounded retry budget:
  по умолчанию 24 ошибки, настройка `IG_WEBHOOK_MAX_MATERIALIZATION_ATTEMPTS`
  ограничена диапазоном 3–100. DB circuit/capacity failures отдельно откладываются
  без такого перехода. Успешное исправленное событие с 278 прежними попытками
  завершится нормально: лимит проверяется только после очередной ошибки.
- BLOCKED ingress включён в существующий technical-debt ledger/inventory;
  исходное событие и защитная остановка сохраняются, проблема не исчезает
  из мониторинга при прекращении retry.
- Legacy UNKNOWN исключает источники канонических delivery effects. Настоящий
  канонический UNKNOWN остаётся отдельным случаем.
- Конечная неполная/отклонённая доставка получает класс
  `canonical_delivery_incomplete:turn_revision`. Неиспользованный template
  fallback и незавершённые in-flight операции не попадают в этот класс.
- Новая финализация связывает незавершённый ответ с существующим механизмом
  `IgFollowUpTask` / `response_debt`. Текст источника, его pending status и
  факты доставки не превращаются в выдуманный успех. Повторное выполнение
  переиспользует задачу; поздний точный receipt допускает финализацию и закрывает
  именно задачу этой ревизии.
- Ограниченная сверка восстанавливает связи исторических ревизий без нового
  запроса к Meta/Gemini, повторной отправки или создания дублей. Она уважает
  живой lease и privacy erasure. Координатор запускает её перед монитором.
- Один устойчивый ключ outbox на текущий набор необработанных операций;
  возраст и смена часа не создают новые уведомления. Новые source IDs создают
  новое наблюдение. Источник истины — БД, не временный cache.
- Перед фактической Telegram-отправкой повторно читается текущий инвентарь.
  Устаревшие алерты завершаются с аудитом. Неполное покрытие откладывает
  отправку и не выдаётся за восстановление. UNKNOWN Telegram не replayится.
- Runtime stall и technical debt уведомляются независимо. Ошибка сохранения
  операторского журнала не скрывает уже доступное уведомление.
- Подтверждение оператором привязано к fingerprint конкретного наблюдения.
  Refresh не подтверждает новые источники автоматически.
- Dry-run координатора выполняет только диагностику расписания.

Миграция БД и изменение схемы не требуются. UI-проекция сохранена для
совместимости; диагностический монитор использует канонические операции.
