# A6 · Медиа, сторис, видео, голос

**Аудитор:** основная сессия, 27.09.2026 · HEAD `c69925d56`

---

## 1. Что реально поддержано

| Тип | Приём байтов | Анализ моделью | Лимиты |
|---|---|---|---|
| Фото (jpeg/png/webp/heic/heif) | да, «owned» в приватном хранилище | да, инлайн | общий бюджет запроса 12 MiB raw → ~16 MiB base64, в пределах 20 MiB |
| Аудио/голос (wav/mpeg/aiff/aac/ogg/flac/m4a/l16/opus/alaw/mulaw/webm) | да | да (инлайн) | 10 MiB/файл |
| Видео (mp4/webm) | да | да (инлайн) | 8 MiB/файл, весь запрос ≤12 MiB raw |
| Сторис-меншн / share / ig_post / ig_reel | метаданные + попытка скачать байты | зависит от того, скачались ли байты | `MAX_OWNED_MEDIA_BYTES = 6 MiB` для UGC-проверки, 2 попытки скачивания |

**Ключевая деталь (правильная, сохранить):** `ig_ugc_assessment.potential_ugc_message()` возвращает `True` и когда байты ещё `pending`/`unavailable`, но `_decision()` для награды требует **owned bytes** + `origin_ok` + `provider_identity_ok` + `personal_worn_apparel` + `target == twocomms`. То есть «нет байтов» ≠ «можно выдать награду» — но нейтральный ответ клиенту всё равно возможен.

## 2. Находки

### F3-MED-01 · Таксономии сторис нет: бот не различает распаковку, ношение своего товара, кастом, отзыв, спонсорское упоминание — **P1 · CODE**
- **Наблюдаемое:** единственная классификация — UGC-оценка для **награды**: `personal_worn_apparel`, `customer_created_content`, `customer_content_confidence`, `brand_match_confidence`, `catalog_matches`, `risk_flags` (`bot_vision.py:65–82`). Нет полей «что это за контент» (распаковка / ношение / кастом / отзыв положительный / отзыв отрицательный / спонсорское упоминание / просто метка / ссылка-стикер).
- **Последствие прямо из брифа (R-09):** владелец описывает кейс — сделка была в Telegram, клиент отметил бренд сторис с видео распаковки; бот ответил «увидели, что вы сделали репост, что вы хотели?». Правильного ответа (тёплая благодарность + уведомление менеджера «можно репостнуть») нет, потому что нет самого понятия «распаковка».
- **Рекомендация:** расширить схему vision-ответа для сторис-контента: `content_kind ∈ {unboxing, wearing_stock, wearing_custom, review_positive, review_negative, sponsor_mention, plain_tag, link_sticker, other}`, `our_brand_visible`, `repurpose_worthy` (стоит ли репостить), `sentiment`. Плюс отдельные шаблоны ответа и текст уведомления менеджеру на каждый `content_kind`. Негативный отзыв → сразу сервис-кейс с высоким приоритетом, без защитного тона.
- **Риск:** расширение схемы увеличивает стоимость вызова; митигировать тем, что вопросы задаются **только** для сторис-типов (`PROVIDER_MEDIA_TYPES`), а не для обычных фото.

### F3-MED-02 · Видео >8 MiB и файлы >12 MiB суммарно просто выпадают из анализа — **P2 · CODE**
- **Наблюдаемое:** жёсткие границы (`INLINE_VIDEO_MAX_BYTES = 8 MiB`, общий 12 MiB raw). Судя по комментарию, введено осознанно под лимит инлайн-запроса 20 MiB.
- **Проблема:** типичное видео распаковки/примерки с телефона — 15–60 MiB. Оно почти всегда превышает лимит → бот получает видео-метаданные без содержания.
- **Рекомендация (план Б по R-41):** детерминированная деградация с честным ответом и без выдумки содержания: «бачу відео, але не можу його відкрити — опишіть двома словами, що там?» + уведомление менеджеру, если тип = сторис-меншн от клиента (потенциальный UGC). Отдельно оценить Gemini File API: на бесплатном тарифе он тоже ограничен, но часто позволяет больший файл; это требует проверки квоты, поэтому — задача-исследование, а не обещание.
- **Дополнительно:** сейчас `potential_ugc_message()` вернёт True для сторис с нескачанными байтами, но **кто** сообщает менеджеру, что UGC не разобран? Проверить, что при `media_capture_exhausted` создаётся задача менеджеру, а не только запись в лог.

### F3-MED-03 · Фото → товар: сопоставление делает сама LLM, без отдельного «не уверен» → каталог-карточки — **P2 · CODE**
- **Наблюдаемое:** `catalog_matches` с `confidence` от vision-модели; `MAX_FP_IMAGES = 2` для отпечатка варианта.
- **Проблема:** нет явного порога «уверенность ниже X → показать 2 ближайшие карточки и спросить», как описано в сценарии 1.5.
- **Рекомендация:** порог + карточки. Дёшево, резко снижает число неверных «это оно?».

### F3-MED-04 · Голос: транскрипция инлайн-аудио есть, но нет правил «голос как вопрос» — **P2 · CODE**
- **Наблюдаемое:** аудио передаётся модели как инлайн, т.е. понимание возможно. Но в промпте/политике нет отдельного указания «если клиент прислал голосовое — ответь коротко на суть, при необходимости переспроси только одно».
- **Рекомендация:** добавить в playbook правило для аудио-хода.

### F3-MED-05 · 31 отклонённый вебхук (`attachment_limit`) и 16 ошибок `signature` не разобраны до конца — **P2 · PROD/GAP**
- **Наблюдаемое (D085 §4.3):** 31/31 `webhook_rejected` = `attachment_limit`; 16/16 `image_download` = `signature`. `ig_webhook_inbox._receipt` поднимает 413 при не-list attachments или >8 вложений.
- **Проблема:** до сохранения в durable-приёмник нельзя отличить честный большой набор от мусора и нельзя восстановить содержимое. Если это реальные клиентские наборы фото — они **теряются молча**.
- **Рекомендация:** синтетический корпус (нормальный набор из 9, смешанный батч, дублирующиеся ретраи) → выбрать ограниченную семантику приёма (например, принимать первые 8 и явно сообщать «бачу 8 з N, надішліть решту») + уведомление менеджеру при отклонении, а не только запись в лог. Для `signature` — собрать примеры MIME (вероятно HEIC/видео-постер) и решить, расширять ли список контейнеров.

## 3. Оценка против требований брифа
- R-06 (фото → товар): реализовано частично, без порога и карточек (F3-MED-03).
- R-09 (сторис): **не реализовано по смыслу** — нет таксономии и правильных реакций (F3-MED-01); менеджер не получает информативного уведомления о UGC.
- R-13 (голос/видео): голос ок, видео ограничено 8 MiB без плана Б (F3-MED-02).
- R-41 (план Б при дорогом медиа): частично — есть честный отказ, но нет уведомления менеджеру и нет решения «что делать» (F3-MED-02/05).

## 4. Идеи
1. **UGC-регистр визуальным слоем:** карточка сторис с превью-миниатюрой, типом контента, решением и кнопками менеджеру (наградить/отклонить/репостить). Данные уже есть (`IgUgcEvidenceAssessment`).
2. **Авто-репост-предложение:** если `repurpose_worthy`, формировать менеджеру готовый текст «можно репостить в сторис, вот миниатюра».
3. **Разбор видео по кадрам:** даже без File API можно взять 3–5 кадров через уже существующий пайплайн изображений (ffmpeg на сервере — проверить доступность) и передать как изображения. Это дешёвое усиление против лимита 8 MiB.

## 5. Вопросы владельцу

- **Q-MED-02:** Спонсорские/партнёрские упоминания (например, стрелковый клуб) — отвечать благодарностью без продажи и всегда уведомлять менеджера?
