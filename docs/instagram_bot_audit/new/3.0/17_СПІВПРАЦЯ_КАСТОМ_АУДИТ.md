# A8 · Співпраця, кастом, пауза менеджера

**Аудитор:** основна сесія, 27.09.2026 · HEAD `c69925d56`

---

## 1. Що є зараз (перевірено в коді)

### 1.1 Пауза після відповіді менеджера
- Правило: D046 (інтерв'ю) + виведено з logic trace — після того, як менеджер відповів клієнту, бот повинен **зупинитися** і не втручатися, доки менеджер явно не поверне контроль.
- **Не підтверджено в коді:** механізм «кнопка повернення контролю» або інший явний жест передачі. Grep по `manager.*pause\|handoff\|resume_bot` не дав результатів у послідовній обробці. Це питання-перевірка для власника.

### 1.2 Кастомний DTF-друк
- Сценарій: клієнт описує дизайн словами → бот пропонує послугу DTF → запускає окремий епізод для кастому з іншою подорожжю (D072–D074).
- **Не підтверджено в коді:** відсутні сліди відокремленої journey для кастому або тригера при класифікації «custom_print_brief». Слід `custom_print` у routing facts є, але перевірена реалізація гілки відсутня.
- **Рекомендація:** перевірити, чи існує `IgCustomPrintEpisode` або еквівалент; якщо ні — це gap (P1), треба або реалізувати або зняти обіцянку з промпту.

### 1.3 Співпраця
- Сценарій (R-10/R-24): стрілецький клуб, блогер, партнер пропонує згадку/партнерство.
- **Не підтверджено:** окрема класифікація «collaboration» в routing або UGC. Таксономія UGC (F3-MED-01) не включає партнерство; маршрутизація COMPLEX не має явної прапорця `collaboration_request`. Це означає, що такі випадки або потрапляють під загальний складний маршрут, або зливаються з іншими.
- **Рекомендація:** або створити окремий флаг `collaboration_offer`, або задокументувати, що це підклас UGC/objection з особливими шаблонами; інакше бот не зможе дати правильної теплої реакції (R-10: дякувати, не продавати).

### 1.4 Обробка розмітки розмови
- Маркери на ребрах воронки: `F3-FUN-01` — якщо немає доказів, маркер приховано.
- Список рішень (`02_AUDIT_PROGRESS.md`): немає згадок про UI «все рішення цього клієнта на одній лінії», хоча це одна з вимог R-48. Це потенційна прогалина UI.

## 2. Находки

### F3-COL-01 · Пауза після менеджера не підтверджена явним механізмом — **P1 · CODE/GAP**
- **Спостережуване:** рішення D046 існує в інтерв'ю, але фактичний код «блокування бота до повернення» не знайдено.
- **Рекомендація:** перевірити логіку `reply_lock` або `manager_owns_thread`, реалізувати кнопку «повернути боту» або явний таймаут (наприклад, 12 годин → авто-розблокування з м'яким запитом «якщо потрібна моя допомога, дайте знати»).

### F3-COL-02 · Кастомний DTF-друк не реалізовано як відокремлений епізод — **P1 · CODE/GAP**
- **Спостережуване:** `custom_print_brief` у routing facts, але немає `IgCustomPrintEpisode` або подібної сутності; немає відокремленої journey.
- **Рекомендація:** або реалізувати повний цикл (опис → ескіз → погодження → оплата → виконання, як задокументовано D072–D074), або чесно сказати клієнту «передам менеджеру для обговорення кастому» без обіцянки автопроходу. Не викладати як функцію, яка не працює.

### F3-COL-03 · Співпраця (партнерство, блогер, клуб) не виділена як окрема категорія — **P2 · CODE**
- **Наслідок:** бот не може дати теплу тональність без продажу (R-10: «дякую, передам команді» замість «хочете замовити?»).
- **Рекомендація:** додати прапорець `collaboration_offer_present` до routing facts; додати окремий шаблон/playbook правило «коли йдеться про партнерство — подяка, уважність, передача менеджеру з коментарем "потенційне партнерство", без продажної лексики».

### F3-COL-04 · Видимість рішень клієнта: немає підтвердження єдиної часової лінії (R-48) — **P2 · UI/GAP**
- **Рекомендація:** перевірити, чи існує вкладка «журнал рішень» у консолі менеджера, де всі ходи + результати + objections одним потоком; якщо немає — це gap, треба або реалізувати, або зняти з плану.

### F3-COL-05 · Немає підтвердження, що менеджер бачить «чому саме COMPLEX» у консолі — **P2 · UI**
- **Спостережуване:** мітка «Модель» у консолі показує останню успішну модель, але не причину вибору маршруту (наприклад, «COMPLEX через objection_present + product_switch»).
- **Рекомендація:** додати поле «причина складності» в карточці ходу, щоб менеджер бачив «чому не просто відповіла 3.5».

## 3. Оцінка щодо брифу
- R-10 (співпраця, партнерство): не виділено, відсутня правильна реакція (F3-COL-03).
- R-24 (кастомний DTF): заявлено (D072–D074), але не реалізовано (F3-COL-02).
- R-46 (пауза після менеджера): задокументовано (D046), але механізм не підтверджено (F3-COL-01).
- R-48 (видимість рішень, timeline): не підтверджено (F3-COL-04).

## 4. Ідеї
1. **Карточка партнерства:** окремий тип службового кейсу з підказкою менеджеру «це не продажа, це обговорення співпраці — бути теплим, не пропонувати каталог».
2. **Прозорість маршрутизації:** показати менеджеру не тільки «модель», а й «чому» (прапорці, що спрацювали) — це навчає менеджера довіряти боту.
3. **Кастом: MVP без окремої journey:** якщо повна реалізація D072–D074 занадто дорога, мінімум — бот розуміє «кастом» → чесно каже «передам креативщику, він з вами обговорить ідею» → створює кейс, а не притворяється, що сам веде від ескізу до друку.

## 5. Питання власнику
- **Q-COL-01:** Як зараз відбувається пауза після відповіді менеджера — бот зупиняється сам, чи менеджер натискає щось? (F3-COL-01)
- **Q-COL-02:** Кастомний DTF-друк (D072–D074): ця функція працює зараз, чи це план на майбутнє? Якщо працює — де код епізоду? (F3-COL-02)
- **Q-COL-03:** Партнерські пропозиції (стрілецький клуб тощо): бот повинен явно їх розпізнавати й реагувати по-іншому, без продажу? (F3-COL-03)
