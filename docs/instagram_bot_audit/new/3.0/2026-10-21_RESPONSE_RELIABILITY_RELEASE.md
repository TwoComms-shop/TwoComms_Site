## Причины и изменения

### Контекст и язык

Перед выкладкойe49 выполнен дополнительный настоящий read-only native `prepare_revision_turn_context` и render для обоих сотрудничеств на productionff746: URBAN/rev236 —1397/2400 estimated tokens, builder7723символа; предложение услуг/rev223 —1272/2400, builder4972. SQL-записи, cache writes и HTTP запрещены диагностикой. Оба текущих контекста помещались уже доe49; исторический `captured_state_exceeds_budget` нельзя объявлять точечно воспроизведённым и устранённым только этим релизом. Старый сбой и закрытое окно не превращаются в разрешение переотправить старую ревизию. После выкладки нужен повтор текущего native reader, отдельно от реальной доставки.

Диагностический replay текущего reader DTO над sealed источниками покупательницы: обязательный блок плана содержал11609 символов, корзина2052, всего13661 при лимите12000. Native capture старой ревизии244 был отклонён `capture_permission_changed` после реального takeover/resume, поэтому этот расчёт не является реконструкцией исходного runtime request и не даёт права на отправку. В projection дублировались таблицы мерок. После удаления дублирования:7775+2052=9827, настоящий builder принимает контекст. Полный план, его digest, разные таблицы regular/oversize и сами измерения сохранены. Настоящее превышение лимита по-прежнему отклоняется.

Исторические сообщения передаются в JSON envelope. Применение удаления цитат к целой обёртке удаляло сам английский текст. Новый language reader извлекает только совпадающее по actor/message/time тело допущенного исторического USER сообщения. Он не меняет исходные тексты, профильный язык или право на выбор товара. Настоящий текущий украинский/русский запрос сохраняет приоритет; кириллическое название товара не заставляет отвечать на другом языке.

Source-only acknowledgement размера2XL теперь согласуется с каноническимXXL,3XL сXXXL. Это не даёт доказательства наличия. В проверке повторного вопроса слово `size` больше не совпадает с частью `oversize`.

### Менеджерская задача и ответ клиенту

Уведомление менеджеру не считается ответом клиенту. Pending business case проецируется ограниченно, с проверкой клиента, источника, reset, permission epoch и purchase episode. Оно объясняет, какой конкретный вопрос ожидает решения; execution debt не становится бизнес-фактом. Закрытие/изменение дела инвалидирует подготовленный ответ. Нет повторного таймера, который циклически генерирует одинаковую реплику.

Общее «уточню у менеджера» больше не закрывает все информационные вопросы и вопросы по посадке. Известная цена, размерная сетка, язык, следующие шаги могут обрабатываться независимо, при сохранении точных ограничений заказа. Поддержаны32 входящих сообщения в burst вместо скрытого ограничения16; невозможный capture становится явным gap, а не отсутствием вопроса.

### Точное время и изготовление

Владелец подтвердил: выбранную футболку нельзя изготовить к22 октября10:00 даже вне очереди. Это решение относится к конкретному обращению, а не ко всем заказам. Общая опубликованная политика: футболки/худи печатаются после оплаты; сезонная приблизительная подготовка1–3дня; время перевозки отдельно. Это не обещание прибытия.

Requirement сохраняет точное локальное время и тип deadline (`departure/arrival/dispatch`), привязанный к timestamp исходного сообщения. `Завтра` не пересчитывается относительно позднего запуска worker. Решение менеджера содержит подписанную requirement identity, конкретные строки и исход `review_pending/impossible`; переход pending→impossible создаёт новую неизменяемую версию. Положительное обещание успеть этим API не вводится.

Оплата/checkout конкретной вещи удерживается, пока клиент явно не согласовал допустимое более позднее получение. «Окей», вопрос, цитата, отказ, гипотеза или запрос международной доставки не являются такой договорённостью. Добавление другой вещи не должно стирать ограничение первой; отдельный QA проверяет реальную последовательность R1→новыйR2, а не только mock проекции.

### Восстановление, очереди и наблюдаемость

`required_context_budget_exceeded` теперь относится к явным pre-provider failures с существующим guarded acknowledgement/debt path. Неожиданное локальное исключение без graph сохраняет только ограниченные stage/code/category/hash в точной operator task. Наличие graph/proposal/effect оставляет прежнего владельца reconciliation; catch-all отправки нет.

Невалидная квитанция SENT помещается в source-bound карантин через существующую задачу. Неизменившийся fingerprint не занимает начало очереди finalization; изменение допускает только повторную проверку доказательства, не новый HTTP. SENT/UNKNOWN и source ledgers не переписываются. Хранилище diagnostics — `task.manager_context`, существующая immutable ссылка `response_debt` сохраняется; schema не меняется.

Ошибка одной housekeeping записи не прерывает свежие клиентские записи; ошибки базы продолжают передаваться наружу. Console сохраняет конечные диагностические коды, фильтруя произвольные строки.

Нагрузочный тест настоящей очереди подтвердил отдельное ограничение: синхронный provider call первого клиента задерживал второго, хотя lease второго свободен. Уменьшение `max_items` само по себе это не решает. Итог исправления scheduling и его MariaDB проверки фиксируется в release checkpoint.

### Параллельное выполнение и резервный ingress

Вместо ожидания одного клиента в главном цикле daemon владеет ровно двумя customer futures без backlog. Для каждого задания остаются отдельное соединение БД, свежие settings и штатная per-client lease/CAS; второй слот не даёт права повторной отправки первому клиенту. Ограничение по подтверждённой ёмкости БД может уменьшить число слотов; неизвестная ёмкость не считается разрешением на расширение. В production preflight подтверждён лимит20 соединений пользователя. При выключении или maintenance сохраняется владение до фактического завершения customer и фоновых потоков; timed join/cancel не объявляют HTTP завершённым. Idle/health не обращаются к Gemini.

При включённом canonical worker главный цикл сначала допускает уже сохранённые webhook-задания, затем выполняет ограниченный2-секундный polling slice и снова заполняет свободные слоты. Это не меняет общий deadline генерации, lease, квоту или приём старых сообщений. Реальные внешние HTTP могут занимать остаток ограниченного запроса, поэтому это не обещание ответа за2секунды.

Аудит обнаружил несовпадение ingest и consumers: native HMAC-подписанный polling принимался в очередь, однако некоторые ветки выбора товара, размерной консультации, назначения покупки, повторного заказа и restock-согласия допускали только webhook. Теперь они используют единый предикат собственного подтверждённого источника с повторной проверкой proof при изменении состояния. Неподписанные/history-only записи и отзыв HMAC не дают права выбора, покупки, отмены либо подписки. Рекламный referral не становится доверенным от одной подписи текста: его отдельный контракт не расширялся.

### Сроки при длинной переписке и переполнении

Старая точная hard requirement сохраняется при добавлении второй вещи, изменении количества и новомR2. Отказ, отрицание отмены, гипотеза, цитата, неполная смена даты не снимают ограничение. Для17/32 собственных входящих сохраняется весь immutable ledger, а bounded review включает актуальные значимые witnesses. Если реальных требований больше16 или bounded history нельзя завершить, записывается подписанный `deadline_history.status=incomplete` и checkout требует уточнить срок. Это не трактуется как отсутствие ограничения. В UI показана причина уточнения; поле `active_hard_requirement_digest` — производная read projection и не меняет подписанный request либо prompt budget.

### Публикация и схема

Новая версия ядра должна публиковаться штатным hash CAS; изменения пяти reviewed scenario modules — отдельным draft/head CAS. Сторонние черновики не публикуются. Приложение использует новый canonical default для будущих settings, поэтому migration0244 синхронизирует только Django state через `SeparateDatabaseAndState(database_operations=[])`: SQL-план содержитno-op; существующий prompt не переписывается миграцией. Действующее ядро меняется только аудируемой публикацией.

## Доставка ответа и границы доказательства

По прямому поручению владельца срочное сообщение покупательнице было отправлено от команды через штатный human reply command. Подтверждены состояниеSENT, отдельная physical part и receipt Meta; ответ виден в авторизованной переписке. Оно объясняет невозможность указанного срока,1–3дня подготовки после оплаты и варианты получения позже, заканчивается вопросом о получателе. Это **операторский ответ, не текст Gemini**; он был отправлен до последующего уточнения владельца об обязательной генерации через Gemini. Повторно его отправлять нельзя. После подтверждения доставки выполнен штатный явный resume: UI сообщил, что ответ уже есть и повтор не создаётся. Read-only проверка подтвердила `bot_paused=false`, `manager_takeover=false`; новым источникам возвращена автоматическая обработка. После отдельной проверки immutable command/partsSENT три старых operator alerts по уже покрытым вопросам рассмотрены штатным `review_reply_debt`: alerts приостановлены аудируемым review, без подделкиSENT старых ревизий или изменения их источников.

Для дальнейших реплик используется штатная генерация Gemini с контролем источников и доставки. Тесты с fakeGemini/fakeMeta подтверждают кодовые свойства, но не живую задержку и тон модели. Ответы двум историческим обращениям нельзя обозначатьSENT без физической квитанции.

## Контрольные сценарии

- Английский → кириллическое название →2XL → короткое `no?`: язык, выбранная вещь, отсутствие повторного запроса размера.
- Два разных chart regular/oversize: все мерки сохранены, обязательный контекст укладывается без увеличения budget.
-32 коротких входящих: все source obligations сохранены, нет тихой потери17-го сообщения.
- Pending менеджерский вопрос + новый независимый вопрос: ответ продолжается, неизвестное решение не выдумывается.
- Невозможный hard deadline → bare okay/отказ/quoted consent/подмена адресата: checkout не открывается.
- Та же вещь + добавленная вторая + новая review: прежнее ограничение не исчезает.
- Poison SENT proof перед healthy receipt: healthy finalization проходит, ошибочный HTTP не повторяется.
- DB disconnect, local pregraph crash, housekeeping poison: правильный owner, конечный reason, нет ложногоSENT.
- B2B, creator, предложение услуг Direct, обычная покупка и смесь намерений: разные briefs, точные передачи руководству.
- Закрытое окно Instagram: private Gemini draft отделён от submit/send и не закрывает customer debt.

## Дополнительные границы

Старая immutable интерпретация получателя в историческом выборе не переписывается новым parser. В production карточка этого выбора ещё может показывать «Для себя», хотя исходное сообщение явно говорит о boyfriend. Подтверждённого native audited API исправления получателя нет: существующий correction API принимает только размер. Нельзя подделывать новое входящее или ретроспективно менять sealed snapshot; новые пользовательские уточнения обрабатываются исправленным reducer. Это отдельная возможность корректировки оператором, а не доказательство уже выполненного изменения старой карточки.

Исходящие inline quoted replies по MID не добавлены: наличие входящего `reply_to.mid` не доказывает поддержку исходящего поля Instagram. Реальные plain-text/multipart receipts сохраняют прежний транспортный контракт.

### Дополнительные находки полной MariaDB QA

Первый pushed commit `e49e82345` прошёл общий Django CI, но native `conversion-context` не прошёл; выкладка остановлена. Часть ошибок была в новых фикстурах: столкновение с migration-owned settings/publication, попытка удалить append-only историю, сохранение старого seeded prompt вместо исходного canonical default. Исправлены фабрики тестов, а не ограничения MariaDB. Отдельный native pool gate прошёл18 тестов без skips, включая разные реальные соединения, одновременную обработку двух клиентов и один lease winner при конкуренции за одного клиента.

Новые фактические дефекты, найденные после этого gate:

- **B2B acknowledgement:** правдивый ответ на пять партнёрских вопросов получалSENT, но план оставлял ложный retail price/color/shipping debt. Введены source-bound `business:*` обязанности: подтверждение передачи целого точного brief закрывает acknowledgement, решение остаётся за командой. Отдельные личные вопросы, включая второй вопрос в том же сообщении, не исчезают. Ассортимент oversize и право использования фото не требуют показа клиенту fit-фотографий.
- **Продолжение B2B:** reader не допускал native `collaboration_review` в pending context. Теперь принимает только доказанное business-case дело с совпадающими source/epoch/reset/episode/proposal/receipt. На «есть новости по партнёрской цене?» можно правдиво ответить об ожидании; это не создаёт новую передачу и не мешает известной личной покупке. Неподтверждённое разрешение использовать фото/партнёрские условия отклоняется до HTTP. Финальные связанные SQLite проверки:129 и затем180 тестов, без skips/failures/errors; provider transport в них тестовый.
- **Python→SQL poll parity:** старые INSERT triggers0230 требовали webhook для restock invitation/answer, хотя Python уже проверял signed current poll. Миграция0245 меняет только два INSERT guard и обратима к точному исходному SQL. Python под client→source locks проверяет настоящий HMAC и sealed source; signed restock envelope сохраняет SHA256 текущих proof bytes; SQL сверяет этот witness с теми же bytes и сохраняет остальные ownership/privacy/clock условия. SQL не объявляется проверяющим Django HMAC. Все14 purpose-poll native тестов прошли на MariaDB без skips; reverse/reapply0245 проверены на одноразовой базе. Требуется также общий native повтор.
- **Равное время двух reviews:** на MariaDB default projection выбралR1/source148 вместоR2/source150 при одинаковом `created_at`, вернул `stale/selection_changed`. Нельзя сдвигать время фикстуры и скрывать дефект: нужен детерминированный выбор latest own source при равном времени, с прежними проверками подписи/currentness.

После исправлений требуется полный повтор на той же одноразовой схеме с0245 и актуальным кодом, затем CI и production verification.
