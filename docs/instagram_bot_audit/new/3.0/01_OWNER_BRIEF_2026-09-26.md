# 01 · Owner brief 26.09.2026 — structured requirements

Source: owner message 26.09.2026 (Russian, dictated, very long). This file restates **every** point as a numbered requirement `R-xx` so nothing is lost. Wording is paraphrased; intent is preserved. Where the owner gave an example, it is kept as an example, not as the only case.

## A. Bot purpose & persona

- **R-01** Bot ("Соломія") must behave as human-like as possible and sell as well as possible, not just answer what the customer wants to hear — answers must be *logically correct* for the business.
- **R-02** No curt/rude openings ("Здравствуйте / До свидания" style); warm, natural, brand tone. Gemini 3.5 Flash Lite is "not the smartest" → prompting/structure must compensate.
- **R-03** Customer should be able to get an answer to almost any question quickly; bot should connect details across the conversation.
- **R-04** Bot must never flatly refuse where a human would gather info first (collaboration requests were being refused — recently corrected; keep and generalise).

## B. Scenarios the bot must handle (non-exhaustive — agent must add more)

- **R-05** Ordinary sale: customer knows the product and asks.
- **R-06** Photo: customer sends a picture; bot identifies which product they want.
- **R-07** Ad referral (Meta Ads): bot must know *which ad* the user came from → which product, which ad tags; subsequent questions refer to that product. Must not re-identify by photo when the referral already tells it.
- **R-08** Collaboration of many types: designer, dropshipper, blogger's manager, physical shop/wholesale, photographer, videographer, other brand, competitor, anything. Bot collects information (like a human would) and hands to manager; never refuses immediately.
- **R-09** Story mention/repost: bot must understand what is in the story/video (unboxing, wearing custom hoodie, wearing stock hoodie, positive/negative review, sponsor mention e.g. shooting club, link sticker present or not). Respond warmly/with a nice comment, thank, notify manager (so manager can repost). Never "I don't understand what is tagged". Example: deal was done in Telegram (bot didn't see it), customer tagged us in a story with an unboxing video → bot must recognise unboxing = advertising our product, thank, notify manager.
- **R-10** Custom (DTF) orders: hoodies (only fleece, no regular), t-shirts (oversize & classic), large/small print — price depends. Bot collects images/model/general understanding, asks for Telegram/WhatsApp contact, hands to manager who will clarify & make mockup. If customer sends own mockup "is this possible?" → "I'll ask our designer and we'll reply".
- **R-11** Size help: gift for girlfriend + height → bot reasons ("oversize L or M both fit; if you want more fitted — X"), explains rather than guessing a single size. Type of clothing, colour, size asked in a smart order; skips what is already known.
- **R-12** Changing mind mid-flow: picked hoodie, size L out of stock/long wait → "then a t-shirt, other print, size M". Different clothing type; oversize vs classic choice. Flow must support going back.
- **R-13** Voice messages, videos (e.g. "size didn't fit" video) — define processing and fallback.
- **R-14** Prompt-injection / spam protection exists but does not notify the manager. Must distinguish spam vs confused human; notify manager appropriately.
- **R-15** Agent must invent further hypotheses (what-if list) and define behaviour for each → `05_SCENARIO_MATRIX.md`.

## C. Funnel visualisation (highest owner visibility priority)

- **R-16** The inline mini-funnel above the chat (compact) and the full funnel map must let an admin understand in ~5 seconds: where the customer started, how they moved, where they are now, where they got stuck, where objections occurred and how the bot answered them, where conflicts were, where they wait for the manager, where the bot was paused, where the manager talked, where unpaused. A different manager must understand the case from the funnel alone without re-reading the chat.
- **R-17** Objection/claim/manager-question markers on the edge between stages (e.g. price objection while choosing product → highlighted on that segment). This existed, a previous agent removed/hid it when asked to make it prettier → **regression to fix**.
- **R-18** No unexplained jumps: if a stage was skipped, the line must show it was skipped and that important info is missing; the bot should clarify it (needs discovery) when there is no understanding.
- **R-19** Show order/time: what was asked first, the path, returns/loops (back to an earlier stage), branch switches (sales → collaboration), not just "blue circles lit because it was once discussed".
- **R-20** Decision nodes: use a different shape (e.g. triangle/diamond) for multi-choice points (collaboration type: designer/dropship/…; product intent: known / needs help / other; fit: oversize vs classic; category) instead of separate full branches. Show which option was taken.
- **R-21** Visual quality: nicer nodes, icons, lines, arrows, positive vs negative outcome semantics; possibly larger layout; possibly animated dots moving along the path to show direction; ring around a node showing waiting time / countdown to the next automatic follow-up (e.g. waiting for payment → time until bot nudges); count of visits to a node. Must be light, clear, beautiful; must not make design worse. Heavier graphics acceptable if perception is much better.
- **R-22** Technically correct: returns, loops, abandoned branches must actually be recorded and rendered, not only drawn.
- **R-23** Generate many ideas per element, choose best, integrate into one coherent design (not first idea).

## D. Overview tab & model operations

- **R-24** Overview tab is confusing: "7 в очереди" — queue of what? "Модель 3.5 Flash Lite отвечает" — models work under different conditions; why show this? Redesign content & console texts.
- **R-25** Gemini: 6 API keys (6 projects); each key has per-model quotas (recorded). Transient server errors ≠ model degradation. Verify grouping, key rotation, errors, fallback; never "kill" a model or project due to a transient error; never break limits.
- **R-26** Routing rationale: chat on 3.5 Flash Lite for volume (≥20 customers/day, many messages); photos/videos go to stronger models (3.8) for accuracy (story reposts especially). Check effort/thinking levels per task and whether errors correlate with effort.
- **R-27** Latency/robustness: server may not respond, network error, server overload/restart → no lost reply; track how many seconds each call took / no response.

## E. Memory & context

- **R-28** Memory must *help Gemini*, not just be stored: next time Gemini sees short context, last messages, how the funnel went, why decisions were made, inconsistencies, who answered (bot/manager), timings ("replied at X, N hours passed → customer might …").
- **R-29** Any agent (even another model) reconnecting must understand the rhythm and logic of recent actions.
- **R-30** Check whether `brand.md` should be read by the bot at all / all the time.

## F. Commerce, conversion, post-purchase

- **R-31** Bot must navigate the site correctly, form correct links, check payment status correctly; understand how the payment webhook is caught; prefer webhooks over infinite cron polling.
- **R-32** Catalogs, cards, opt-in buttons must display correctly and beautifully; opt-in offered with logic and charm ("bro, we can notify you when it arrives; subscribe to get a discount after you receive the order"), extending Meta's messaging window. On Nova Poshta pickup trigger → thank you, invite story tag / unboxing / review → reward (discount next purchase / priority customer / promotions). Must be designed properly.
- **R-33** Points & gifts: minor, not a main priority, but present: "you'll get N points; I can transfer them to the site; use for % discount or raffles; if unused within a period they are donated to ZSU (Armed Forces), never burn". Must be designed carefully.
- **R-34** Custom collaboration (see R-10) fully worked out.

## G. Engineering quality

- **R-35** Never break what works (history: typing/seen disappeared, stopped replying to stories). Every plan item must state why it will not break existing behaviour.
- **R-36** Server resources: shared hosting with other services; optimise; remove dead functions/requests; fix crons that spam Telegram with errors.
- **R-37** Use newest/smartest solutions, update libraries if beneficial, background helpers if useful.
- **R-38** Logging system for later analysis: record decisions (memory read?, funnel followed?, what should have happened) so that in 1–2 weeks another agent can analyse logs and find errors, leaks, memory misuse, funnel deviations.
- **R-39** Tests must be meaningful (not tests for the sake of tests); consider prod DB ≠ local DB; plan how to test.
- **R-40** Where uncertain → test; or write conditional plan steps ("run test X; if metric ≥ Y do A else B").
- **R-41** Free Gemini tier constraints: if something (e.g. video) is too expensive, define plan B (e.g. notify manager without answering).
- **R-42** Consider psychology/marketing techniques with justification of *why* they work and *how* to give them to Gemini so it actually follows them.
